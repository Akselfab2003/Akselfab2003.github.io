The problemBefore

Each release was a long checklist: 40+ manual steps and 15+ hand adjustments spread across Excel sheets and .bat scripts. It was slow, and every manual edit was a chance for one release to come out differently from the last.

Part of the process ran against an external vendor's service, integrated through SOAP and WCF.

What I builtSolution

I built a CLI application that performs the full release, and made it the foundation of an Azure Pipeline. Product teams and managers start a release by filling in seven inputs — versions, names and similar — and nothing else is done by hand.

The most demanding part was the external SOAP integration. The API had no batch operations, so every item became its own call — more than 200 per release.

  • Worked through the generated SOAP client code to pinpoint where calls failed.
  • Added retry logic around each individual call.
  • Verified the result of every call, so the pipeline knows the release actually landed.

OutcomeResult

Releases went from a long manual checklist to a pipeline run with zero manual steps. Less manual work, and releases that are done the same way every time, by anyone on the team.

Risk & reliabilityDesigned for
Failure mode: partial success

With 200+ separate calls to a remote service and no batch transaction, the dangerous outcome isn't a crash — it's a release that half-succeeds without anyone noticing.

Retrying each call and verifying every result means the system knows the release worked, rather than assuming it did.
