The problemBefore

The legacy .NET solutions carried a large number of old project and DLL references that were no longer used. Removing them safely meant first knowing what actually depended on what. At the same time, developers waited 40 minutes for the CI pipeline to tell them whether a change was good.

Seeing the dependencies

Illustration of the idea behind the tool: projects as nodes, references as edges. Faded nodes are referenced by nothing that ships. Not real HBK data.

What I builtDependency x-ray

I built a Python dependency visualizer that identified the dependencies between .NET projects and drew them as a node graph. Once the structure was visible, it was possible to see which references actually mattered.

Using it as part of the legacy upgrade, I helped remove more than 3,000 old and unused references — a mix of project and DLL references — improving overall code quality.

CI/CDFeedback loop

In the same upgrade work I found a way to speed up the CI/CD pipeline, cutting the time before a developer gets feedback on a change from 40 to 25 minutes.

Also at HBKProduct work

Not all of it was infrastructure. I also built a dial component for one of the products — it displays data from sensors and other sources, and changes colour when values move into a warning or alert range so critical readings stand out. The gauge on the front page of this site is modelled on it.

Less surface, faster checks

Every unused reference is code that ships but that nobody watches. Removing 3,000+ of them means fewer things to patch, audit and trip over.

A faster pipeline matters too: checks people don't have to wait 40 minutes for are checks they actually run.
